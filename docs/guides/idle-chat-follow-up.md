# Idle-Chat Follow-Up Sequences

When a customer goes idle after an agent reply, Omni can fire a configurable
sequence of follow-ups on a schedule (e.g. 3 min → 5 min → 30 min). Each
follow-up is generated by the agent with full conversation context — the
synthetic "please follow up" instruction never leaks into the visible history;
only the agent's rendered message is sent as a normal outbound message.

> Wish: `.genie/wishes/idle-chat-follow-up/WISH.md`
> Issue: [automagik-dev/omni#404](https://github.com/automagik-dev/omni/issues/404)

---

## How It Works

1. **Arm.** When an outbound agent message is sent, the follow-up lifecycle
   hook resolves the active config (closest scope wins: chat → instance →
   agent → off). If a sequence is enabled, a row is upserted into
   `chat_follow_up_state` with `nextFireAt` set to the first interval.
2. **Sweep.** An in-process cron (`*/15 * * * * *`) selects every row where
   `nextFireAt <= now` and `disarmReason IS NULL` under
   `FOR UPDATE SKIP LOCKED`, emits `chat.idle_timeout` for each, then advances
   or disarms the row.
3. **Fire.** A user-space automation listens for `chat.idle_timeout`, calls
   the agent with `promptOverride` (so the synthetic prompt never reaches chat
   history), and sends the agent's response as a normal outbound message.
4. **Disarm.** Inbound customer messages, handoff activation, chat archive,
   and the 24 h WhatsApp BSP messaging window all disarm the sequence with a
   reason recorded on the row.

## Configuring a Sequence

Use the `/v2/follow-up/:scope/:id` REST endpoints or the CLI.

### CLI

```bash
# Set on an agent
omni follow-up set agents <agent-id> '{"enabled":true,"schedule":{"kind":"fixed","intervalsMinutes":[3,5,30]},"maxFollowUps":3,"promptTemplate":"Ping {{chatName}} — {{minutes}}m"}'

# Set on an instance from a file
omni follow-up set instances <instance-id> @./followup.json

# Set on a chat via stdin
cat followup.json | omni follow-up set chats <chat-id> -

# Read / clear
omni follow-up get chats <chat-id>
omni follow-up unset chats <chat-id>
```

### REST

```http
PUT /v2/follow-up/agents/:id       # body: FollowUpSequenceConfig
PUT /v2/follow-up/instances/:id
PUT /v2/follow-up/chats/:id        # merges into chats.settings.followUpConfig
GET /v2/follow-up/{scope}/:id
DELETE /v2/follow-up/{scope}/:id
```

### Config Schema

```ts
{
  enabled: boolean,                 // default: true
  schedule:
    | { kind: 'fixed',    intervalsMinutes: number[] }
    | { kind: 'exponential', initialMinutes: number, factor: number, maxMinutes: number },
  maxFollowUps: number,             // 1..50 — hard cap
  promptTemplate: string,           // placeholders below
  stopOutsideMessagingWindow: boolean, // default: true (WhatsApp BSP 24 h guard)
  showTypingIndicator: boolean,     // default: true
}
```

Template placeholders available to `promptTemplate` and to automation actions
via the `chat.idle_timeout` payload:

| Placeholder           | Meaning                                                   |
|-----------------------|-----------------------------------------------------------|
| `{{syntheticPrompt}}` | The rendered prompt from the sweeper                      |
| `{{minutes}}`         | Minutes since the agent's last reply                      |
| `{{sequenceIndex}}`   | Zero-based follow-up index about to fire                  |
| `{{attemptNumber}}`   | One-based attempt number — prefer this in LLM prompts     |
| `{{totalAttempts}}`   | Total attempts configured (`maxFollowUps`) — LLM-friendly |
| `{{chatName}}`        | Chat display name when known                              |

**Resolution hierarchy.** The closest scope wins. A chat-level `enabled: false`
disables follow-ups for that chat even if the instance or agent has it on.

## Example Automation

The sweeper emits `chat.idle_timeout`. Users author the "what to say" logic as
a normal automation — see `docs/examples/automations/idle-follow-up.yaml` for
a ready-to-ship template using `call_agent.promptOverride` → `send_message`.

The key invariant: the `call_agent` action renders `promptOverride` and passes
it as the **sole message** to the agent. The rendered override is NOT written
to chat history. Only the agent's response reaches the customer via
`send_message`.

## Events

Every state transition emits a structured event for observability.

| Event                    | When                                                | Key payload fields                                           |
|--------------------------|-----------------------------------------------------|--------------------------------------------------------------|
| `follow_up.armed`        | Sequence armed or re-armed after a fire             | `chatId, instanceId, agentId, sequenceIndex, nextFireAt`     |
| `chat.idle_timeout`      | Sweeper fires — consumed by user-space automations  | `chatId, instanceId, agentId, sequenceIndex, attemptNumber, totalAttempts, syntheticPrompt, minutesSinceLastAgentReply, chatName?` |
| `follow_up.fired`        | Sweeper successfully fired a follow-up              | `chatId, instanceId, agentId, sequenceIndex, firedAt, syntheticPrompt` |
| `follow_up.skipped`      | Sweeper encountered an error processing a row       | `chatId, instanceId, agentId, sequenceIndex, reason`         |
| `follow_up.disarmed`     | Sequence disarmed for any reason                    | `chatId, instanceId, agentId, sequenceIndex, reason`. Note: `sequenceIndex` is `-1` when the active row can't be read at disarm time (e.g. the row was already cleared). |
| `chat.handoff_activated` | Chat was handed off to a human/other agent          | `chatId, instanceId, ...` (disarms with `handoff`)          |
| `chat.archived`          | Chat was archived or muted                          | `chatId, instanceId, ...` (disarms with `archived`)         |

### DisarmReason

`customer_replied | handoff | archived | window_expired | sequence_complete | agent_error | send_failed`

## Channel Capabilities (Plugin Authors)

The sweeper and the lifecycle hooks consult two small, pure helpers in
`@omni/core/automations` to stay channel-agnostic. If you are authoring a
channel plugin and want your channel to participate:

### `channelHasMessagingWindow(channelType)`

Declares whether your channel enforces a 24-hour post-inbound messaging
window (WhatsApp Cloud / BSP). Edit the `CHANNELS_WITH_MESSAGING_WINDOW` set
in `packages/core/src/automations/follow-up/capabilities.ts` when adding a
new channel that requires the same guard. The sweeper disarms with
`window_expired` when `now − lastInboundCustomerMessageAt > 24 h`.

### `channelSupportsTypingIndicator(channelType)`

Declares whether your channel can emit a typing / presence indicator. Listed
alongside the messaging-window set in the same file.

### `TypingIndicatorSender`

When your `ChannelPlugin` implements `sendTyping(instanceId, chatId, duration)`,
it satisfies the `TypingIndicatorSender` contract and can be handed to
`playTypingIndicator()` via a resolver. The helper is a silent no-op when the
channel is unsupported or the sender throws — typing is best-effort.

```ts
import { playTypingIndicator } from '@omni/core';

await playTypingIndicator({
  channelType: instance.channel,
  instanceId,
  chatId,
  showTypingIndicator: config.showTypingIndicator, // from resolved follow-up config
  resolver: (ch) => channelRegistry.getPlugin(ch) ?? null,
});
```

## Invariants

- **The synthetic prompt never appears in chat history.** The lifecycle
  service and the `call_agent.promptOverride` path are the only two entry
  points where the prompt flows — neither writes it back as a user message.
- **Sequences survive API restarts.** All timer state lives in
  `chat_follow_up_state`; the sweeper resumes from `nextFireAt` on boot.
- **No double-firing.** `FOR UPDATE SKIP LOCKED` in the sweeper's transaction
  guarantees only one worker claims a due row per tick.
- **Re-arming refreshes.** When a new outbound agent message lands on a chat
  with an existing row, the row is upserted with `sequenceIndex = 0`,
  `disarmReason = null`, and a fresh `nextFireAt`.
