# Council: How should Omni's current design (repo <omni-checkout>, version 2.261030.x) improve so every system talks to each other, and so ONE specific agent can subscribe to exactly the events it cares about? Omni today has five overlapping ingress/egress surfaces: channels (instances, message.received), webhook sources (credential-less ingress, custom.* events, liveness), connectors (sealed credential + typed actions + event subscriptions, ClickUp only), automations (trigger event + conditions + one action: webhook | send_message | emit_event | log | call_agent | connector.call), and durable event consumers (named cursor, pull/ack, long-poll, SSE). Agents are reached via providers (agno, webhook, openclaw, ag-ui, claude-code, a2a, nats-genie). The owner is confused about how a specific agent subscribes to events. Target use: an agent team (Herdr terminals driven by `hc`, a main bot plus squad captains, on a Mac with no inbound port) must react to all software-lifecycle events (GitLab MRs, notes, pipelines, issues, releases) and be reachable from WhatsApp/Telegram/Slack, with Omni as the bus hosted at <internal-host>.

## Lenses
### architecture
Verdict: support-with-conditions
Confidence: medium
Key evidence:
- The answer to 'how does one agent subscribe' already exists, as a pull mechanism that is not tied to agents. A durable event consumer takes an eventType (exact match or a trailing-* prefix glob), excludeTypes globs, and up to 20 payload conditions combined with AND. The conditions support eq, neq, gt, lt, contains, regex and exists, and they are evaluated server-side (packages/api/src/schemas/openapi/event-consumers.ts CreateConsumerSchema; services/event-consumers.ts evaluateConditions). Delivery is outbound-only: pull with long-poll waitMs, ack, or SSE with heartbeat and reconnect (routes/v2/event-consumers.ts). That fits a Mac with no inbound port. This answers explicit unknown #1: consumers filter by type and by payload.
- GitLab events need no connector and no schema change. Webhook sources already have a public ingress, POST /api/v2/webhooks/ingress/:source (app.ts:552). It is auth-exempt and verified only by the source's signatureConfig, which supports algorithm 'token-match' (services/webhooks.ts verifySignature) and so matches X-Gitlab-Token. eventTypeMapping {source:'header'} turns one multiplexed URL into custom.{source}.{token} (resolveWebhookEventType), so 'X-Gitlab-Event: Merge Request Hook' becomes custom.gitlab.merge-request-hook.
- The GitHub version of this already ships as a CLI source preset: hmac-sha256, eventTypeMapping on X-GitHub-Event, an idempotencyKeyTemplate on a delivery header, registered payload schemas, and ensureProviderWebhook (packages/cli/src/commands/sources.ts). The smallest GitLab slice is a second PRESETS entry. It is not a new ConnectorManifest, so the connector contract stays untouched.
- Connectors do not fit multiplexed lifecycle webhooks. A subscription holds exactly ONE eventKey and ONE targetAutomationId (schemas/connectors.ts:89-92), and a parsed key that does not match is an 'ignored' ack (connector-sdk types.ts parseDelivery doc). matchesFilters only compares JSON values for exact equality on dotted paths (services/connectors.ts:157). connectorTargetMatches fires only the one target automation (core/automations/engine.ts:46). One GitLab hook URL would therefore need N subscriptions and N GitLab hooks.
- A push-style per-agent subscription also exists. The agent eventManifest 'accepts' entries are compiled into managed automations, one per entry, with eq-only filters and a call_agent action (services/manifest-compiler.ts:1-22,144). `omni agents graph` shows who consumes what (cli/commands/agents.ts:573). call_agent goes through the agent's provider, so it needs the provider to be reachable from Omni. Having this push path next to the pull consumers, with nothing linking them, is the main source of the confusion.
- Agents are a first-class entity (routes/v2/agents.ts, with eventManifest storage in services/agents.ts updateManifest). Durable consumers have no agentId, though. Ownership exists only for scoped consumers, as ownerKeyId (services/event-consumers.ts:296-340). This partly answers explicit unknown #2: an agent can own a manifest but cannot own a consumer.
- Scoped consumers fail closed on instance-less rows: instanceScopeClause uses inArray(omniEvents.instanceId, ...) (services/event-consumers.ts:381). Webhook and trigger events take instanceId only from optional metadata (services/webhooks.ts:727,795). A per-key isolated consumer therefore cannot receive custom.gitlab.* events today.
- Unscoped consumers are open to any caller: canAccessConsumer returns true when !consumer.scoped (services/event-consumers.ts:348-354). pull, ack, stream and delete all require only events:write (constants/scopes.ts:200-205). Any agent key can therefore advance or delete another agent's cursor.
- nats-genie is chat-only. It publishes omni.message.{instance}.{chat} and subscribes to omni.reply.{instance}.> (core/providers/nats-genie-provider.ts header). The API connects to NATS_URL, which defaults to nats://localhost:4222 (api/src/index.ts:110). It is not a lifecycle-event bus for remote agents unless NATS is exposed.
Risks or objections:
- Two subscription models that do not know about each other, push (a manifest compiled to call_agent automations) and pull (anonymous durable consumers), are what keep 'how does an agent subscribe' unclear. Adding a third mechanism, such as a GitLab connector or a NATS fan-out, would add to the confusion, not fix it.
- Cursor interference between agents. Unscoped consumers can be pulled, acked or deleted by any key that has events:write. One squad captain's bug, or a prompt-injected agent, can skip or wipe another agent's backlog.
- Event spoofing inside the bus. events:write, the scope consumers need, also authorizes POST /events/trigger for any custom.* type (scopes.ts:495, routes/v2/webhooks.ts:181-185). An agent key could forge custom.gitlab.* events. Publishes are tagged source:'manual-trigger' (services/webhooks.ts:728), but I could not verify that a consumer filter can select on that metadata rather than only on rawPayload.
- Untrusted text flows directly to agents. GitLab note and MR bodies, and WhatsApp, Telegram and Slack messages, arrive as payload fields in what the agent reads. Nothing in the consumer path marks these as untrusted. That is left to agent-side discipline.
- Using connectors for GitLab events would cost N subscriptions times N GitLab hooks per project, each with its own sealed secret. When the GitLab category set changes, operators have to edit hooks on both sides. A GitLab category with no matching subscription is ack'd as ignored, so events would be silently missing, which goes against record-and-report.
- The SSE stream never moves the stored cursor and is refused for shared consumers (routes/v2/event-consumers.ts stream docs). An agent that streams but forgets to ack will replay on every restart. A competing-captains (shared) setup has to use pull with leases, not SSE.
- Liveness of the GitLab source matters. A dead hook (GitLab disables hooks after repeated failures) looks the same as a quiet repo unless expectedIntervalSeconds and heartbeat supervision are set, as the GitHub preset does with 86400.
Required conditions:
- Bring GitLab in as a webhook-source preset ('gitlab' next to 'github' in cli/commands/sources.ts): signatureConfig {algorithm:'token-match', header:'X-Gitlab-Token'}, eventTypeMapping {source:'header', header:'X-Gitlab-Event'}, an idempotencyKeyTemplate on GitLab's per-delivery UUID header, and registered schemas for MR, note, pipeline, issue and release, with strict mode once those schemas exist. Do not build a GitLab ConnectorManifest for events.
- Use the durable event consumer as the single answer to 'agent X subscribes to events'. Document one recipe: one consumer per agent role (for example agent.captain-backend: eventType custom.gitlab.*, excludeTypes for noise, payload conditions on project.path_with_namespace or labels). Delivery is SSE or long-poll from the Mac, the agent acks after handling, and it replies through the outbound omni send verbs.
- Smallest code change: let the existing agent eventManifest 'accepts' entry declare delivery 'pull'. manifest-compiler.ts would then reconcile a durable consumer, named for example agent.<name>, in place of a call_agent automation, keeping the same diff/converge semantics and the same `omni agents graph` view. Agents then have one declaration surface for both push and pull. No enum, route or connector change is needed.
- Before several agents share Omni, close the cursor-isolation gap. Add an owner, either agentId or ownerKeyId, to consumers that are not instance-scoped, and restrict ack/delete/stream to that owner or an admin key. Scoped consumers already do this, but they fail closed on instance-less custom.* rows.
- Give agent keys a scope that allows pull/ack/stream but not POST /events/trigger, or make the source/provenance of a journaled row filterable. Then a forged custom.gitlab.* event cannot reach a captain.
- Mark payload text fields from ingress (GitLab note bodies, chat text) as untrusted data in the consumer envelope or the agent recipe. Agents must never get the GitLab token or the source's signature secret. The secret is sealed server-side and token-match only compares it.
- Deferred-complexity triggers. Add a GitLab connector only when agents need credentialed GitLab actions, such as posting MR notes or retrying pipelines, without holding a token: actions through connector.call, events still through the source. Add multi-event connector subscriptions (an eventKey list, or the subscription fanning out to several automations) only when a second connector provider needs them. Expose NATS or a2a to remote agents only when pull latency or the per-key SSE stream cap (resolveStreamMaxPerKey) is measured to be insufficient.
Unknowns:
- Unverified: whether GitLab 19.5 CE supports HMAC-signed webhooks (a signing token) in addition to X-Gitlab-Token. If it does, the preset should use hmac-sha256 on the raw body. Otherwise token-match is a shared-secret header with no protection against replay or body tampering beyond TLS.
- Unverified: the exact name and stability of GitLab's per-delivery UUID header (I believe it is X-Gitlab-Event-UUID) to use in the idempotencyKeyTemplate.
- Unverified: whether a consumer's payload conditions can match the journal's source/provenance metadata (for example excluding 'manual-trigger'), or only fields inside rawPayload.
- Unverified: whether <internal-host> exposes NATS (port 4222) or the a2a endpoint publicly. The code defaults NATS_URL to localhost. How a2a delivers to a host with no inbound port was not examined.
- Unverified: whether channel events (message.received from WhatsApp, Telegram, Slack) carry payload fields that let a consumer select one bot's or one chat's traffic precisely, beyond instance scoping.
- Unverified: whether the deployed <internal-host> version (described as 'latest') matches this checkout (2.261030.11) for consumers, sources presets and manifest compilation.
- Unverified: the per-key SSE stream limit default and whether it fits one stream per Herdr terminal on a single shared key.

### delivery
Verdict: support-with-conditions
Confidence: medium
Key evidence:
- The answer to 'how does one agent subscribe' already exists: a durable consumer (one cursor per name) with a type filter that is exact or a trailing-* glob, excludeTypes, payload conditions run through the automation matcher (eq/contains/regex/exists, AND or OR), pull/ack, long-poll and SSE (packages/api/src/services/event-consumers.ts:5-40; packages/db/src/schema.ts:3698-3785; CLI `omni events follow --consumer`, packages/cli/src/commands/events.ts:1482). This settles the first open question: the server filters by both type and payload.
- The agent reads by pulling. Pull, long-poll and SSE are outbound calls from the Mac, so they work without an inbound port. call_agent and webhook/agno/ag-ui push providers cannot reach the Mac. nats-genie publishes to omni.message.{instance}.{chat} and subscribes to omni.reply.{instance}.> (packages/core/src/providers/nats-genie-provider.ts:1-16), so it only works if the Mac can reach NATS, which I could not verify.
- Webhook sources already cover GitLab ingress with no code change: the signature algorithms include 'token-match' (schema.ts:2989), compared in constant time (webhooks.ts:108-112). eventTypeMapping by header emits custom.{source}.{token} (webhooks.ts:132-154), so X-Gitlab-Event would become custom.gitlab.<sanitized-name>. idempotencyKeyTemplate dedupes redeliveries through the journal's unique index (webhooks.ts:446-460). One source URL takes every GitLab hook category, which fits GitLab sending all selected categories to one URL.
- Connector deliveries are journaled as connector.event, with the envelope keys provider, eventKey and subscriptionId at the top level and the provider body under rawPayload (services/connectors.ts:181-205, 992-1006). A durable consumer can therefore filter `eventKey eq ...` on connector events too.
- A connector subscription has exactly one providerEventKey. A delivery with a different eventKey, or one that fails the filters, returns 202 {ignored:true} (services/connectors.ts ~905-908). If a GitLab hook ticks more categories than its subscription's key, the extra categories are dropped silently while the hook still looks healthy to GitLab.
- Connector journal rows are written with no instanceId (connectors.ts:996-1006). instanceScopeClause applies inArray(omniEvents.instanceId, ...) and fails closed on an empty set (event-consumers.ts:380-384). So a scoped (owned) consumer can never see connector.event rows. The same likely holds for custom.* rows from webhook sources, but I did not verify that.
- Agents have no identity in Omni's access model. api_keys has no agent_id column (schema.ts:614-690). A consumer's ownership is ownerKeyId, and only when it is scoped. durable_consumers has a globally unique name and no tenant column (schema.ts:3698-3790). Unscoped consumers can be seen, pulled, acked or deleted by any key with events:* scope.
- targetAutomationId is a required uuid (schemas/connectors.ts:73, 91). connectorTargetMatches returns true when the target is missing (core/src/automations/engine.ts:46-52). Making the target optional therefore makes every connector.event automation fire. That is a change in behaviour for existing ClickUp automations, not an additive migration.
- Each API key may hold 5 open SSE streams by default (EVENT_STREAM_MAX_PER_KEY, event-consumer-stream.ts:57-58, 110). A main bot plus several captains streaming on one key would be refused (429).
- The connector subscription test route runs parse→filter→claim→publish with the signature check bypassed and a random idempotency key (connectors.ts ~696-742). It proves the wiring but not dedupe or verification. Tests already exist to copy: connector-ingress.test.ts, event-consumers.test.ts, event-consumers-scoped.test.ts, event-consumer-stream.test.ts. The latest connector migrations are 0089_connectors.sql and 0090_connector_event_ownership.sql.
Risks or objections:
- A per-category connector subscription design fails silently: an eventKey mismatch or filter miss returns 202 ignored, and I found no subscription counter or liveness check that would show it. That breaks the failure doctrine of making failures loud at configuration time.
- Agents are not isolated from each other. Connector events (and probably custom.* rows) can only be read through unscoped consumers, so any agent key with events:* can ack another agent's cursor past events it has not handled, or delete its consumer. Acceptable for one trusted team on one host; a breach once a second trust domain appears.
- Making targetAutomationId optional with a nullable column would make every existing connector.event automation fire on every delivery, because of the no-target branch at engine.ts:50. Rollback would also need a data fix.
- SSE stream cap: with one key per Herdr agent, or a shared key, 5 streams each is easy to hit. A refused stream that falls back to nothing leaves an agent deaf with no visible error.
- MR notes, issue comments and chat text arrive as journal payloads and reach agents verbatim. If the bridge on the Mac pastes them into an `hc` prompt without fencing them as untrusted data, a comment can inject instructions into an agent.
- Consumer filter paths depend on the surface. For connector rows, eventKey and provider sit at the top level and the GitLab body is under rawPayload.*. For webhook-source rows the shape differs. A wrong dotted path matches nothing, and because the cursor advances over scanned rows, the agent silently skips events.
- Version skew: this assessment is against repo HEAD 2.261030.11, while <internal-host> was just updated to an unknown build. Behaviour such as 0082 scoping, 0083 access filter and 0089/0090 connectors may differ on the server.
- Building a GitLab connector module first is the largest change with the least payoff for receiving events. It pays off only when an agent needs typed outbound actions (connector.call), and it inherits the single-key-per-subscription silent-drop problem.
Required conditions:
- Phase 0, precondition: confirm the version <internal-host> reports matches a build that has migrations 0089/0090 and the consumer features cited, and that the installed CLI matches the server, before relying on any behaviour above.
- Phase 1 (no code): receive GitLab through ONE webhook source per GitLab project or group hook. Use signatureConfig {algorithm: 'token-match', header: 'X-Gitlab-Token'}, eventTypeMapping by header 'X-Gitlab-Event', an idempotencyKeyTemplate built on GitLab's per-delivery UUID header, and expectedIntervalSeconds only if a heartbeat exists. Rollback: delete the hook or source; nothing needs a migration.
- Phase 1 (no code): each agent subscribes through ONE durable consumer named after the agent, unscoped, with eventType 'custom.gitlab.*' (captains add payload filters on project path) and a second consumer for message.received on its channel instance. Pull it from a single bridge process on the Mac that long-polls or holds one SSE stream per consumer, stays under EVENT_STREAM_MAX_PER_KEY, and hands events to `hc` panes as fenced untrusted data. Rollback: delete the consumers.
- Ship evidence, recorded on the live host: (a) GitLab 'Test hook' for each category (MR, note, pipeline, issue, release) returns 2xx and lands one journal row with the expected custom.gitlab.* type; (b) a wrong X-Gitlab-Token is refused; (c) redelivering the same delivery creates no second row (dedupe counter bumps); (d) each agent's consumer pulls only its filtered rows, ack advances, and after a disconnect it resumes after the last ack; (e) a filter test against a real journaled row proves the dotted path matches; (f) an injected note such as 'ignore previous instructions' reaches the agent only inside the data fence.
- Put a GitLab connector module (one provider module registered at boot, no enum, route or action change) off until an agent needs typed write-back (post an MR note, approve, retry a pipeline) through connector.call with sealed credentials. When it lands, either use one connector subscription URL per GitLab hook category, or first make an ignored delivery visible (counter plus a doctor or status line). Tests to add: parseDelivery fixtures for each X-Gitlab-Event, a verify() test with a constant-time token, and eventKey mismatch counted rather than silent.
- Only make targetAutomationId optional after changing the no-target branch in connectorTargetMatches to fire nothing, and test that existing ClickUp automations are unaffected. Ship it as its own change behind its own trigger: a connector event that needs no automation.
- Put agent identity and isolation off (agent-owned consumers, scope by owner key for instance-less rows such as connector.event and custom.*, tenant-scoped consumer names) until a second trust domain appears (a non-owner agent, a second tenant, or an agent key exposed outside the Mac). Then it needs its own migration with its own tests in the event-consumers-scoped.test.ts style.
Unknowns:
- Unverified: whether webhook-source custom.* journal rows carry an instanceId. If they do not, scoped consumers cannot read them, just as with connector.event.
- Unverified: the exact token X-Gitlab-Event produces after sanitizeEventToken (for example 'Merge Request Hook' should become 'merge-request-hook'), and whether GitLab 19.5 sends a per-delivery UUID or Idempotency-Key header to use in idempotencyKeyTemplate.
- Unverified: whether GitLab 19.5.1 CE signs webhooks with HMAC or sends only X-Gitlab-Token. It does not change the design: token-match and a custom ConnectorManifest verify() (connector-sdk types.ts:101) both cover a constant-time token check.
- Unverified: whether GitLab CE 19.5 offers group-level webhooks. If not, every project needs its own hook, which multiplies setup and drift.
- Unverified: whether any counter, metric or liveness check records connector 202 {ignored:true} outcomes.
- Unverified: whether the NATS server behind <internal-host> can be reached from the Mac, which nats-genie needs. I did not check how a2a reaches a local agent without an inbound port.
- Unverified: the ingress body-size limit for webhook sources and connector routes compared with large GitLab pipeline or MR payloads.
- Unverified: the build actually deployed on <internal-host>, and whether its consumer, connector and webhook behaviour matches repo HEAD 2.261030.11.
- Out of scope for this lens: updating the installed omni client. Not assessed and not done.

### product
Verdict: support-with-conditions
Confidence: medium
Key evidence:
- Omni already has a first-class way for an agent to subscribe to events. The `agents` table has an `eventManifest` column with `accepts`/`publishes` (packages/db/src/schema.ts ~L399-430, RFC #925 G4a). `ManifestCompilerService` (packages/api/src/services/manifest-compiler.ts) turns each `accepts` entry into a managed automation: a trigger on the event type, `eq` conditions joined with AND, and a `call_agent` to that agent. The CLI exposes it as `omni agents manifest get|apply <id> --file` (packages/cli/src/commands/agents.ts L11-12). The `publishes` allowlist is enforced on `emit_event` (packages/api/src/plugins/automation-actions.ts L274-296, #987). The owner's confusion is about how to find this, not a missing capability.
- The manifest is not mentioned in docs/architecture/event-system.md or any other architecture page. grep finds it only in docs/runbooks/agent-publish-governance.md, docs/cli/design.md and docs/api/endpoints.md. The architecture docs never explain how one agent subscribes to events, so the 'five overlapping surfaces' read as unrelated features.
- The durable consumers answer the stated unknown: they filter on the server by both type and payload. CreateConsumerSchema (packages/api/src/schemas/openapi/event-consumers.ts L78-120) takes `eventType` (exact type or a trailing-* glob such as `custom.gitlab.*`), up to 20 `excludeTypes`, up to 20 AND payload `filters` (operators eq, neq, gt, lt, gte, lte, contains, not_contains, exists, not_exists, regex), an access filter, `shared` (competing consumers with leases), and `scoped` (the owner is an API key: `ownerKeyId` plus instanceIds, schema.ts ~L3774-3778). Delivery is pull/ack, long-poll or SSE, and every one of these is an outbound request from the client. That makes it the delivery mode that works on a Mac with no inbound port.
- GitLab ingress already works through a webhook source, with no new connector. `WebhookEventTypeMapping` with `source: 'header'` (schema.ts ~L3063-3087, services/webhooks.ts `resolveWebhookEventType`) maps `X-Gitlab-Event` to `custom.gitlab.<token>`. The `token-match` signature algorithm (schema.ts L2989-3000) checks a header that carries the secret itself, which is how `X-Gitlab-Token` works. The idempotency template, liveness and heartbeat also apply (connector-contract.md). So one GitLab hook URL that sends every category becomes distinct types such as `custom.gitlab.merge-request-hook`, which a consumer can glob.
- The connector subscription model does not fit GitLab or GitHub-style multiplexed webhooks. Each subscription has exactly one `eventKey` and one `targetAutomationId` (packages/api/src/schemas/connectors.ts `CreateSubscriptionBodySchema`). A delivery whose parsed eventKey differs is answered `202 ignored` (services/connectors.ts L904-905). Filters are exact JSON equality joined with AND (`matchesFilters`, L157). `connectorTargetMatches` (core/automations/engine.ts L46-52) fires only the one target automation. Covering MRs, notes, pipelines, issues and releases this way would take one GitLab hook and one automation per event key per project.
- Connector verification supports `hmac-sha256` or a `custom` verify function (packages/connector-sdk/src/types.ts L90-103), so a GitLab connector could support `X-Gitlab-Token` through `custom` without changing the contract. Adding a provider stays a single module.
- The names are already split. Connector deliveries are journaled as one type, `connector.event`, with the key in the payload, while webhook sources emit `custom.{source}.{event}`. An agent's manifest or consumer has to know which ingress produced an event to subscribe to it.
- Manifest `accepts.filter` supports only equality (schema JSDoc: 'equals semantics'; the compiler maps it to `eq` AND). Consumers have the full operator set. These are two subscription grammars with different expressiveness.
- Compiled manifests always call `call_agent`, which pushes to the agent's provider. The `nats-genie` provider publishes to `omni.message.{instance}.{chat_id}` and subscribes to `omni.reply.{instance}.>` (packages/core/src/providers/nats-genie-provider.ts header), so it reaches a Mac only if the Mac dials a NATS server it can reach.
- The CLI on PATH reports 2.261030.9; the repo's packages/cli/package.json is 2.261030.11.
Risks or objections:
- Adding a sixth surface, or a GitLab connector just to receive events, would make the confusion the owner describes worse. Every needed piece exists, but nothing tells a user which one to use.
- Connector-based GitLab ingress means N hooks times M projects, each with its own secret and automation. That is high operator toil, and a misconfiguration fails quietly as 202 `ignored`, not as an error.
- Having two subscription grammars (manifest equality-only versus consumer operators) and two naming schemes (`connector.event` plus a payload eventKey versus `custom.gitlab.*`) means one agent's subscription breaks if a provider moves from webhook source to connector.
- Push-only manifests (`call_agent`) do not reach a Mac with no inbound port unless NATS or another outbound bridge is reachable. Teams will reach for tunnels or ngrok, which widens the attack surface.
- Consumers belong to an API key (`ownerKeyId`), not an agent. Per-agent attribution, revocation and quota therefore depend on key hygiene, and a shared tenant-wide key lets any agent read every event.
- GitLab note, MR and issue payloads carry free text written by outsiders. Both delivery paths hand raw payloads to agents. Without a stated contract that this text is data only, an MR comment is a prompt-injection channel into squad captains that can act through connector.call or send_message.
- The client was older than the server (2.261030.9 installed against a .11 repo, and the server's version is unverified). New flags such as consumer `shared`/`access`, manifest commands or `--consumer` could fail or behave differently until the CLI and SDK are updated.
Required conditions:
- Publish one canonical answer to 'how does agent X subscribe' before building anything: the agent manifest `accepts` for agents Omni can push to (call_agent), and a scoped durable consumer per agent, named after it (for example `agent.<name>`, pull or SSE), for agents behind NAT such as the Herdr/hc Mac. Put it in docs/architecture/event-system.md and overview.md, with a table mapping channel, webhook source, connector, automation and consumer onto that one path.
- Smallest code change, if any: let a manifest `accepts` entry choose `delivery: pull`, which compiles to a durable consumer owned by the agent instead of a `call_agent` automation. Reuse the consumer filter grammar so manifest filters gain the full operator set. Do not change the connector contract, routes, enums or action types.
- GitLab slice v1 needs no new code: one webhook source per GitLab instance or group, using `eventTypeMapping` header `X-Gitlab-Event`, a `token-match` signature on `X-Gitlab-Token`, and an idempotency template keyed on GitLab's delivery or event UUID header (the exact header is unverified). Agents subscribe with `custom.gitlab.*` plus payload filters such as project path, labels or action.
- Defer a GitLab connector until a squad must act on GitLab (post an MR note, change labels, trigger a pipeline) through credentials Omni holds. When it lands, ingress should still run through the webhook source, or the connector should gain a per-connector multiplexed endpoint. Trigger for that: a second multiplexed provider (GitHub) needs connector ingress, or more than 3 subscriptions per connector get configured.
- Settle event naming so an agent subscribes once, regardless of ingress: either connectors also emit `custom.{provider}.{eventKey}`, or the docs state that `connector.event` plus payload `eventKey` is the stable name. Choose one before a second connector ships.
- Give each agent its own scoped API key (consumer `scoped: true`). Agents read events and call connector actions only through Omni and never see provider credentials. Treat inbound GitLab and chat text as untrusted data in agent prompts, and rely on the manifest `publishes` allowlist to limit what each agent may emit.
- Update the installed CLI and SDK to match the <internal-host> server version before testing consumer `shared`/`access`, manifest compile or SSE stream behavior.
- Triggers for deferred complexity: per-agent consumer quotas or identity-owned consumers when more than one team or tenant shares a key; server-side fan-out to multiple targets per connector subscription when one provider event must reach 2 or more agents through push; a NATS or a2a outbound bridge only if pull or SSE latency fails a measured target (for example, more than 5s p95 from MR note to captain reaction).
Unknowns:
- Unverified: whether GitLab 19.5.1 CE sends an HMAC signature header, or only `X-Gitlab-Token`, and which delivery or event-UUID header suits the idempotency template.
- Unverified: whether `nats-genie` or `a2a` can reach a Mac with no inbound port in practice. That depends on whether a NATS server reachable from both <internal-host> and the Mac exists. Only the provider's topic layout was read.
- Unverified: whether `call_agent` with a compiled manifest needs an instance or chat context that a GitLab `custom.*` event lacks (CallAgentActionConfig has `agentId` and an optional `providerId`; its full response-routing behavior was not read).
- Unverified: whether journaled `connector.event` rows can be read by durable consumers in the same way as `custom.*` rows (for example, whether the internal-origin rows are visible to a scoped consumer).
- Unverified: which Omni version is deployed at <internal-host>, and whether it matches repo 2.261030.11.

### security
Verdict: support-with-conditions
Confidence: medium
Key evidence:
- Durable consumers already filter on the server, which answers explicit unknown 1. CreateConsumerSchema (packages/api/src/schemas/openapi/event-consumers.ts) takes eventType as an exact type or a trailing-* glob, plus excludeTypes (up to 20 globs) and filters (up to 20 AND conditions on the payload, using the automation matcher: eq, neq, gt, lt, contains, exists, regex and so on). The regex operator has a dangerous-pattern check and an input-length cap (packages/core/src/automations/conditions.ts checkRegex).
- Pull fits a Mac with no inbound port: pull with long-poll and the SSE stream are outbound HTTPS from the agent host (routes/v2/event-consumers.ts). Each stream is capped per key and per process, and it lives at most EVENT_STREAM_MAX_LIFETIME_MS before it must reconnect, which re-authenticates and works as a revocation ceiling.
- Consumers are not owned by an agent unless they are scoped. canAccessConsumer (services/event-consumers.ts:349-354) returns true for every unscoped consumer, so any key that holds events:write can see, pull, ack or delete another agent's consumer by name. The only owner binding is scoped:true, which needs instanceIds. instanceScopeClause (line 381-384) then filters rows by omni_events.instance_id and fails closed on an empty set, so a scoped consumer can never receive instance-less events such as GitLab or connector events.
- Pulling events needs write-tier authority. scopes.ts lines 201-205 map pull, ack and stream to events:write, and events:write also authorizes POST /events/trigger (line 495), which emits arbitrary custom.* events (webhooks.ts:180-185 checks only the custom. prefix). An agent key that can listen can therefore also forge custom.gitlab.* events that fire automations, including connector.call actions.
- Webhook sources can already receive GitLab's multiplexed hook on one URL. The public route POST /api/v2/webhooks/ingress/:source is auth-exempt but verified: the signature algorithm can be token-match, a constant-time compare of a sealed secret (services/webhooks.ts:593-617, timingSafeEqualStrings), which fits X-Gitlab-Token. Unknown, unsigned and badly signed requests all get the same 401, and the route is IP rate-limited (app.ts:552). With eventTypeMapping {source:'header', header:'X-Gitlab-Event'} each delivery is emitted as custom.{source}.{sanitized-token}, for example custom.gitlab.merge-request-hook (resolveWebhookEventType and sanitizeEventToken, webhooks.ts:119-155).
- Connector ingress is one URL per subscription, and each subscription has exactly one eventKey and one targetAutomationId (schemas/connectors.ts CreateSubscriptionBodySchema). The sealed HMAC secret is checked before anything is journaled, and unknown subscriptions, unopenable secrets and bad signatures all return the same 401 (app.ts:591-606; docs/architecture/connectors.md). Under ConnectorVerification (connector-sdk/src/types.ts) a GitLab X-Gitlab-Token check would need kind 'custom' with a hand-written verify(), and nothing in the SDK makes that function constant-time.
- Credentials stay sealed and on the server. ConnectorActionContext.credentials is 'never logged or returned', the response schemas have no credentials or verificationSecret field (schemas/connectors.ts header comment), connectors:invoke is classed as write-tier (tenancy/scope-projection.ts:89), and instance-restricted keys get 403 CONNECTORS_TENANT_SCOPED (routes/v2/connectors.ts). So an agent that writes to GitLab through connector.call or POST /connectors/:id/actions/:action never sees the PAT.
- Agents are already first-class (unknown 2 is partly answered). They have /agents CRUD, identities, and a manifest at PUT /agents/:id/manifest (scopes.ts:78-87). The manifest's 'accepts' entries are compiled into managed automations (G4b, automations/types.ts managedByAgentId), and its 'publishes' list is enforced when an agent emits events (G4c, core/src/schemas/agent-manifest.ts). Delivery still goes through call_agent and a provider, and runChatlessCallAgent passes ctx.messages to the provider with no marking that the content is untrusted (plugins/automation-actions.ts:84-128).
- nats-genie (unknown 4) connects with only servers:natsUrl and passes no auth options (providers/nats-genie-provider.ts:335-341). It publishes to omni.message.{instance}.{chat} and takes agent replies from omni.reply.{instance}.>, so whoever can publish on that subject can speak as the agent. Reaching it from the Mac would mean exposing Omni's NATS bus beyond the server.
- The connector binding gate (engine.ts:46-52, connectorTargetMatches) does not narrow a connector.event that has no targetAutomationId. Today such an event cannot be forged through /events/trigger, because that route allows only custom.* types.
Risks or objections:
- Cross-agent interference and eavesdropping: unscoped consumers have no owner. Any agent key with events:write can read another squad's GitLab or chat stream, ack its cursor (silently skipping its events), or delete it. Scoping is the only isolation, and it cannot express events that have no instance (GitLab, connectors, system.*).
- Privilege bundling: a listen-only agent must hold events:write, which also lets it emit custom.* events. A prompt-injected agent (for example one obeying an MR comment that says 'emit custom.gitlab.merge-request-hook with action=merge') could forge lifecycle events that trigger automations with connector.call side effects, unless every such automation is managed by the manifest so the publishes gate applies. Hand-authored automations are not governed by it.
- Untrusted text reaches agents unlabelled: GitLab note bodies, MR descriptions, commit messages and WhatsApp, Telegram or Slack text flow through the journal and call_agent into prompts. No sanitizing or untrusted envelope was found on the automation or consumer path. Anyone who can comment on a project the hook covers can inject instructions into an agent that holds hc terminal control on the operator's Mac.
- Over-broad data exposure: GitLab hooks can carry confidential issue and confidential note events. Once journaled, every tenant key with events:read (GET /events, /events/search) can read them, and a broad consumer glob such as custom.gitlab.* would copy them to every agent.
- Token-match is a static bearer secret: GitLab's X-Gitlab-Token is not a body signature, so anyone who captures it (proxy logs, a leaked hook config) can forge deliveries. There is no timestamp or replay window; only the idempotency template dedupes redeliveries.
- Exposing NATS for nats-genie, or opening an inbound port for the webhook, a2a or agno providers, would widen the attack surface far beyond outbound HTTPS pull. The nats-genie client shows no subject-level authorization.
- Taking the connector route for GitLab ingress multiplies secrets and URLs: one subscription per eventKey means one GitLab hook per category, each with its own secret. A hand-written 'custom' verify() could compare tokens with == and open a timing side channel.
- Agent manifests let an agent route events to itself: an agents:write key can rewrite its own accepts and publishes lists and so widen what it receives and emits.
Required conditions:
- Smallest secure path. Ingress: one webhook source named 'gitlab' on the public ingress, with token-match against X-Gitlab-Token, eventTypeMapping on header X-Gitlab-Event, and an idempotency template on a per-delivery GitLab header. Egress to GitLab: a GitLab connector whose sealed PAT is used only through typed actions. Agent subscription: one durable consumer per agent, with an eventType glob, excludeTypes and payload filters, pulled over outbound HTTPS with long-poll or SSE from the Mac. No inbound port, no NATS exposure. This adds a module and a webhook source, with no enum, route, scope, trigger or action change, so the connector contract property is kept.
- Bind consumers to agents before more than one agent shares a tenant: give each consumer an owner key (or agent id) that does not depend on instance scoping, so scoped:true or an equivalent works for instance-less events. Until then, give each agent a unique consumer name and treat names as non-secret, because any events:write key can reach them.
- Split the consume authority from the emit authority. Pull, ack and stream should require a consumer scope (for example events:consume) separate from the events:write that /events/trigger needs. If that is deferred, mint each agent key without events:write and run the pull through a server-side relay. The trigger to do this: the first agent key issued with events:write.
- Every automation that turns an event into a GitLab or chat side effect must be manifest-managed (managedByAgentId set), so the publishes gate applies, and must use typed connector actions with a destructive-action allowlist: no merge, delete or approve without a human confirmation step.
- Wrap event payload text delivered to agents (consumer rows and call_agent messages) in an explicit untrusted-data envelope, and have the hc runtime refuse to execute shell or terminal commands taken from event content without operator approval.
- Do not subscribe the GitLab hook to confidential issue or note events, or keep them out of every agent consumer with excludeTypes or filters, until journal reads are scoped per agent.
- Rotate the X-Gitlab-Token through the webhook source secret, keep it out of reverse-proxy and access logs, and switch to HMAC if GitLab 19.5 offers a signed-webhook header.
- Deferred-complexity triggers: (a) multi-URL or multi-event connector subscriptions only when a second provider needs Omni-owned credentials for ingress as well; (b) per-agent journal read scoping when a second human or tenant-external agent joins; (c) NATS for the Mac host never, unless NATS gets per-subject credentials and TLS.

- Unverified: whether GitLab 19.5.1 CE offers an HMAC-signed webhook header in addition to the static X-Gitlab-Token, and which per-delivery id header it sends (X-Gitlab-Event-UUID, Idempotency-Key) for use as the idempotency template key.

Verdict: oppose
Confidence: medium

That settles the open unknown: consumers DO filter by payload on the server, not only by type.

The public ingress POST /api/v2/webhooks/ingress/:source (packages/api/src/app.ts:552) requires a signature config. verifySignature in services/webhooks.ts:585-620 supports `token-match` on any named header, which matches GitLab's X-Gitlab-Token, as well as hmac-sha256 and hmac-sha1. resolveWebhookEventType (webhooks.ts ~130-155) maps a header to `custom.<source>.<sanitized token>`, so a GitLab source with eventTypeMapping {source:'header', header:'X-Gitlab-Event'} would produce custom.gitlab.merge-request-hook, note-hook, pipeline-hook and so on, on one URL. Risks or objections:
- Scope creep against the stated constraint 'prefer the smallest design change'. ## Synthesis
Decision: proceed-with-conditions
Consensus: All five lenses reach the same substantive finding, though the dissent lens votes oppose. Omni does not need a redesign or a sixth surface for one agent to subscribe to exactly its events, because the mechanism already exists. A durable event consumer filters on the server by type: an exact type or a trailing-* glob, plus up to 20 excludeTypes globs. It also filters by payload: up to 20 conditions using eq, neq, gt, lt, contains, regex, exists and the other matcher operators. It delivers by pull/ack, long-poll or SSE, and every one of these is an outbound HTTPS call. That fits a Mac with no inbound port. This answers the owner's question directly: one named consumer per agent role.

GitLab ingress should be a webhook source, not a connector. The setup is one URL at /api/v2/webhooks/ingress/:source with signatureConfig {algorithm: token-match, header: X-Gitlab-Token}, plus eventTypeMapping {source: header, header: X-Gitlab-Event}. That maps deliveries to custom.gitlab.<sanitized-token>, such as custom.gitlab.merge-request-hook. Add an idempotencyKeyTemplate keyed on a GitLab per-delivery header. A config-only GitHub recipe or preset already exists to copy.

All lenses agree the connector model is the wrong fit for GitLab events. Each subscription carries one eventKey and one targetAutomationId, a delivery that does not match is acknowledged with a silent 202 ignored, and the hook count grows as categories × projects. A GitLab connector is deferred until agents need credentialed write-back such as MR notes, labels or pipeline retry through connector.call. When it arrives, ingress still goes through the webhook source.

The confusion comes from two existing answers that nothing links: push, where the agent eventManifest 'accepts' list compiles to call_agent automations, and pull, through anonymous durable consumers. Push via call_agent cannot reach the NAT'd Mac unless the Mac can reach NATS, which no lens verified. All lenses agree the result should be a single documented 'how agent X subscribes' recipe with GitLab as the worked example.

Every lens names the same risks:
- **Cursor interference:** unscoped consumers have no owner, so any key with events:write can pull, ack or delete another agent's cursor.
