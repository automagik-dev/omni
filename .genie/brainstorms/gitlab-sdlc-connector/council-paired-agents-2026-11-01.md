# Council: Rethink how agents work in Omni (repo <omni-checkout>, 2.261030.x), by EXTENDING, not removing, the current model. Today Omni integrates agents the old way: providers (agno, webhook, openclaw, ag-ui, claude-code, a2a, nats-genie) and the call_agent automation action, where Omni calls the agent synchronously and waits for a callback; agent eventManifest 'accepts' compile into call_agent automations. The owner's direction, verbatim: 'omni probably needs to recognize / pair agents. the old omni agent method (focused on integrations) is outdated. we need the other way around, like you, this specific claude code, registering as an omni [agent] that's consuming specific resources ... the current way agent works needs to be rethought (not removing the old) but extending it so that it can work with anything, i dont want future omni to have direct agent integrations at all... sync calls with agent callbacks are so 2023'. Proposal to assess: an agent (any harness: a Claude Code session, a Codex or omp terminal, a Herdr bot with a permanent identity, a remote service) PAIRS with Omni and becomes a first-class principal with its own credential; it DECLARES the resources it consumes (event types and payload filters across channels, webhook sources such as custom.gitlab.*, connector events, other agents' emissions) and the verbs or typed actions it may use; Omni DELIVERS asynchronously to it (durable per-agent cursor, pull/long-poll/SSE, outbound-only so it works behind NAT) and the agent ACTS through the existing outbound verbs (omni say/send) and typed connector actions; the legacy provider/call_agent path stays as one adapter on top of the same subscription model. This must also serve an event-driven 'collective consciousness' for a ~40-agent team, where Brain (a separate memory engine with session hooks and context injection) turns Omni deliveries into injected context.

## Lenses
### architecture
Verdict: support-with-conditions
Confidence: high
Key evidence:
- Agent integration today is a closed set: providerSchemas is a fixed 7-value enum (packages/db/src/schema.ts:323), with a switch in packages/core/src/providers/factory.ts:39 and another in packages/api/src/plugins/agent-dispatcher.ts:4830 (a 6801-line file). So the connector property ('one module registered at boot, no enum change') does NOT hold for agents now. Its main structural gain is that a paired agent touches none of these three places.
- The async delivery layer already exists. A durable consumer is name + filter + cursor over the totally ordered journal (omni_events.journal_seq, unique index at schema.ts:2099), delivered at-least-once with a cursor through pull/ack, long-poll (PULL_MAX_WAIT_MS 30s, scan limit up to 500, packages/api/src/services/event-consumers.ts:197-198) or SSE. Shared (competing) consumers already exist (event-consumers.ts:24-32). All of it is outbound-only from the agent's side, so it works from a Mac behind NAT.
- There are three separate subscription concepts today: manifest accepts compiled into a call_agent automation (packages/api/src/services/manifest-compiler.ts header), the durable consumer (event-consumers.ts:5-9), and the connector subscription of one eventKey plus targetAutomationId (packages/connector-sdk/src/types.ts:33-37; packages/core/src/automations/engine.ts:46-52). The smallest unifying change: add agentId to durable_consumers, have the manifest compiler (which already reconciles managed rows by managed_by_agent_id) emit consumers, and keep call_agent as a push-delivery adapter.
- The agent principal mostly exists already. The agents table has ownerId pointing to persons and an eventManifest (schema.ts:399-428). platform_identities.agent_id landed with an actor XOR check (schema.ts:1521, 1561). omni_events.agent_id (schema.ts:2017) and messages.sender_agent_id (schema.ts:1834) carry attribution. actor-model.md:84-122 defines Agent as 'registered, not discovered'. The agents table has no credential column, and api_keys has no agentId.
- Device pairing already mints a non-human agent credential. DEVICE_CLIENT_KEYS.unfold mints a companion key named 'agent' with ['messages:send','events:read','events:write','instances:read'] (packages/api/src/login/config.ts:96-100), narrowed under the operator's ceiling, and api_keys.parentKeyId enforces child-never-wider lineage. Pairing can therefore reuse device login plus a companion key bound to an agent row, with no new principal type.
- A consumer and an emitter use the same scope. events:write authorizes consumer create, delete, pull, ack and stream, and also POST /events/trigger (packages/api/src/constants/scopes.ts:201-205 and :495). So today's paired 'agent' companion key can forge any custom.* event.
- The publishes gate does not run on the agent's direct emit path. checkPublishAllowed only applies when the engine passes managedByAgentId on an automation emit_event (packages/api/src/plugins/automation-actions.ts:549-556). POST /events/trigger is not gated by agent identity at all (packages/api/src/routes/v2/webhooks.ts:201).
- Consumer ownership is weak. canAccess returns true for every caller when a consumer is unscoped, and also for any instance-unrestricted key even when it is scoped (event-consumers.ts:353-354). Scoped consumers page only rows whose instance_id is in their set (event-consumers.ts:381-383), so custom.* and connector events with a null instance_id are excluded (trigger takes instanceId as optional, webhooks.ts:201-215).
- Filter languages differ. Manifest accepts filters are flat dot-path equality joined with AND (packages/core/src/schemas/agent-manifest.ts:52-60). Consumers take AutomationCondition[] evaluated by evaluateConditions (eq/neq/gt/lt/contains/regex/exists) plus excludeTypes.
- The consumer path has no loop guard and no untrusted-text fencing. grep finds no senderInstanceId or loop handling in event-consumers.ts; isInstanceSenderLoop exists only in the automations engine (engine.ts:562). The only untrusted-input sanitising in providers is control-character stripping in packages/core/src/providers/openclaw/provider.ts:21.
- Fan-out capacity is mostly fine. SSE caps are 5 per key (DEFAULT_STREAM_MAX_PER_KEY) and 100 per process (DEFAULT_STREAM_MAX_PER_PROCESS, packages/api/src/services/event-consumer-stream.ts:56-58), so 40 agents on one SSE stream each fit on one replica. Long-pollers at 30s cost about 1.3 indexed range scans per second in aggregate.
- Turn context for 'omni say' is stored per key (api_keys.contextChatId, packages/api/src/routes/v2/context.ts:74). An agent holding one key while acting on async deliveries from several chats would race on that single context, unless it uses explicit targets or a child key per thread.
- A2A already supports streaming as well as round trip (packages/core/src/providers/a2a-provider.ts:1-8: trigger() and triggerStream() with message/stream). It is still a push provider dispatched by Omni, so it fits as one more adapter over a subscription and not as the delivery model.
Risks or objections:
- Security regression if pairing ships on today's scopes. A paired agent holding events:write can forge any custom.* event, pull or ack another agent's unscoped consumer, and move that consumer's cursor so the other agent silently loses events (scopes.ts:201-205,495; event-consumers.ts:353).
- Agents' declared publishes is not enforced on the path paired agents will actually use (POST /events/trigger). The manifest becomes advisory and the agents graph misleads (automation-actions.ts:549-556).
- Storm risk across a 40-agent collective. Agents acting via omni say or trigger produce events that other agents' consumers pull back. With no loop guard or self-exclusion on consumers, chains of agents can amplify without bound (engine.ts:562 guards only automations).
- Prompt injection reaches Brain. Deliveries carry raw message and comment text in rawPayload. If Brain's context injector places payload text where it reads as instructions, any WhatsApp sender or GitLab commenter can steer 40 agents; Omni has no envelope-level fence today.
- Instance scoping fails closed. An agent consumer scoped for least privilege silently sees no custom.gitlab.* or connector.event rows (null instance_id), so operators will widen to unscoped consumers, which have no ownership (event-consumers.ts:381-383).
- Concept sprawl if the proposal adds a fourth subscription table instead of extending durable_consumers. Accepts automations, consumers and connector targetAutomationId would then drift apart, and the connector D7 rule (one subscription, one target automation) would need a second target kind.
- Two filter dialects (manifest flat equality vs consumer conditions) leave 'agent X subscribes to Y' ambiguous unless one dialect is chosen as canonical.
- Turn context is stored per key, so concurrent async deliveries can misroute an agent's omni say to the wrong chat (context.ts:74).
- Lag accounting counts all journal rows past the cursor, not matching rows only (event-consumers.ts:119-121). A busy GitLab source will make every agent look lagged, which makes doctor and health signals noisy.
- Lease or cursor contention on long-lived Herdr bots and on Claude Code sessions that disconnect: at-least-once redelivery after a session restart means agent actions must be idempotent. Nothing in the proposal states that for agent-side verbs.
Required conditions:
- Make the durable consumer the single subscription concept. Add a nullable agentId (FK to agents) to durable_consumers, and have manifest-compiler reconcile accepts entries into agent-owned consumers. Keep call_agent automations as an opt-in push-delivery adapter compiled from the same entry (e.g. delivery: push|pull). No new subscription table.
- Bind credentials to agents. Pairing reuses device login companion-key minting (login/config.ts) to mint a key carrying agentId, a child of the owner's key (parentKeyId lineage), shown once and revocable per agent. No new principal type.
- Split scopes before any agent pairs. Add a consume-only scope (e.g. events:consume) for consumer pull, ack and stream, kept separate from events:write and POST /events/trigger. The paired-agent profile gets consume plus messages:send plus the declared typed connector actions only.
- Enforce ownership by agentId. An agent key may see, pull, ack or delete only consumers with its own agentId, regardless of the scoped flag or whether the key is instance-unrestricted. The legacy behaviour for agent-less consumers stays as it is.
- Enforce publishes at the trigger route. When the calling key carries agentId, POST /events/trigger runs checkPublishAllowed against that agent's manifest and stamps omni_events.agent_id. A refusal goes to the dead-letter queue as publish_not_declared, exactly as the automation path does.
- Give agent scoping a rule for rows with no instance. An agent consumer may name custom.* and connector source types it is granted explicitly (by webhook source or connector subscription id) instead of failing closed on a null instance_id.
- Exclude an agent's own events by default. Agent-owned consumers drop rows whose omni_events.agent_id equals their own agentId (opt-in to include them), and loop-depth or causation bounds are carried through causationId.
- Define a fenced delivery envelope as a contract. Untrusted text is delivered only in a marked data field with provenance (channel, sender, source), never in instruction position. Brain's context injector must honour that fence, and that is a Brain-side acceptance criterion.
- Choose one filter dialect. The manifest accepts filter compiles to AutomationCondition[] (equality stays as sugar), so manifest and consumer semantics are identical and the agents graph shows one thing.
- Agent verbs on async deliveries name an explicit target (chat or instance from the delivery) or use a per-thread child key, never the key's single mutable contextChatId.
- Legacy providers and call_agent stay unchanged in behaviour. No provider enum value or dispatcher case is removed, and the new path adds none.
- Name the triggers for deferred work. Shared/competing consumers per agent pool apply when two sessions of one agent must split work. waitForReady applies when Brain needs filled payloads. Raise the SSE cap or move to multiplexed per-agent streams when agents x streams approaches EVENT_STREAM_MAX_PER_PROCESS (100). Add journal archival or partitioning when consumer lag scans become measurable. Push delivery to non-NAT agents (webhook) remains the legacy adapter until it is needed.
Unknowns:
- Unverified: event volume of a busy GitLab project and its effect on per-agent scan cost. I estimated pull mechanics (indexed range scans, limit up to 500, cursor advances past non-matching rows) but did not measure real journal growth or the cost of regex conditions over large rawPayloads.
- Unverified: whether omni_events.agent_id is populated today for emissions made by agents through omni say or POST /events/trigger. The self-exclusion loop guard depends on it.
- Unverified: whether device login can be invoked headlessly for a non-human, remote or permanent identity (a Herdr bot or a remote service), or whether it needs an interactive WhatsApp owner approval per pairing (packages/api/src/plugins/device-login.ts describes owner approval via self-chat).
- Unverified: how typed connector actions are authorized per key today, and whether 'the verbs or typed actions it may use' can be expressed with the existing scope and profile model without a new allowlist column.
- Unverified: how A2A task lifecycle events (agent.a2a.task_*) would map onto consumer deliveries, given the a2a provider today only supports Omni-initiated trigger/triggerStream.
- Unverified: Brain's side of the contract, meaning whether its session hooks can hold a long-poll or SSE consumer per session and dedupe at-least-once redeliveries across session restarts.
- Unverified: behaviour of lag/caughtUp metrics and EVENT_STREAM_MAX_LIFETIME_MS reconnection under 40 concurrent agents across replicas.

### delivery
Verdict: support-with-conditions
Confidence: medium
Key evidence:
- Most of the delivery machinery already exists. Durable consumers keep a cursor over the journal (cursor = last acked journal_seq, backed by the unique index omni_events_journal_seq_uq; migration 0064 lines 5-6 and 32-34). Delivery is at-least-once, with pull/ack, shared leases and redelivery when a lease expires (packages/api/src/services/event-consumers.ts lines 5-30). Pull, long-poll and SSE are all outbound from the agent, so an agent on a Mac behind NAT can use them without a new transport.
- The scoped consumer path cannot serve the headline use case (custom.gitlab.*, connector events). instanceScopeClause returns inArray(omniEvents.instanceId, consumer.instanceIds) (event-consumers.ts:381-383), and a row whose instanceId is NULL never matches an IN list. POST /events/trigger makes instanceId optional (routes/v2/webhooks.ts:189, 202-216), so custom.* rows can carry no instance. canAccessConsumer grants access by instance overlap, not by identity (event-consumers.ts:344-353).
- No credential is bound to an agent. The api_keys schema has parent_key_id (migration 0088) and instanceIds, but no agent_id column. The agent dispatcher finds an agent's 'scoped key' by a naming convention, agentKeyNameCandidates(agentRecord.name, tenantId) followed by apiKeys.findByName (plugins/agent-dispatcher.ts:2935-2945). That join is implicit; pairing would make it explicit.
- Durable consumers carry no agent identity. 0082 added scoped, instance_ids and owner_key_id (with no FK, on purpose), and nothing else. Its header says global consumers are pullable, ackable and deletable by any events:write key (0082 lines 1-17).
- /events/trigger accepts any custom.* type under events:write (scopes.ts:495; webhooks.ts:184). It does no check against publishes or the manifest, so a paired agent key with events:write could fake custom.gitlab.* events that other agents then consume as if they came from the webhook source.
- The manifest already declares 'agent X accepts Y'. AgentEventManifestSchema allows up to 200 accepts entries, each with an event and a filter (packages/core/src/schemas/agent-manifest.ts:46-92). The compiler is the only writer of managed rows and reconciles desired against existing state with no churn (services/manifest-compiler.ts:1-22). Compiling an accepts entry into an owned durable consumer is one more desired-shape branch, and call_agent compilation stays as it is.
- 0082 is the migration template: hand-written, additive, IF NOT EXISTS, default off, no BEGIN/COMMIT. 'Existing rows and every create without the option keep today's behaviour exactly.' A nullable agent_id on durable_consumers and api_keys follows it, and rolling back means leaving the column unset.
- Test harnesses already exist where the agent-ownership tests would go: routes/v2/__tests__/event-consumers-scoped.test.ts, event-consumers-stream.test.ts, __tests__/event-consumers-postgres.test.ts and keys-device-child.test.ts. CI runs from .github/workflows/ci.yml.
- Device pairing is a human approval step. plugins/device-login.ts approves a Better Auth device code when the owner sends it from their own WhatsApp self chat and mints the owner's grant (mintConnectGrant with userId: owner.id, line 190). It does not create an agent principal, but it is the UX pattern that could gate minting an agent key.
- The per-key SSE cap is 5 by default (services/event-consumer-stream.ts:57, 83-84). With one key per agent this is that agent's own budget, so it does not block ~40 agents. It only becomes a problem if agents share one key.
Risks or objections:
- If agents get scoped consumers before ownership moves to identity, consumers on custom.* and connector.event deliver nothing and give no error. The failure is invisible, the kind the operator's doctrine forbids.
- If pairing hands out events:write before /events/trigger checks publishes, any of the ~40 agents can inject custom.gitlab.* or other agent-emission events that the rest of the collective trusts as real. That is a cross-agent prompt-injection path straight into Brain context.
- If agents fall back to unscoped consumers to get custom.* delivery, any other agent's events:write key can pull, ack or delete their cursors (0082 header). One misbehaving agent could ack another agent's queue and starve it.
- Cost of scanning: lag counts all journal rows past the cursor, not only matches (event-consumers.ts:119), and the cursor moves over scanned rows. With ~40 sparse-filter agents on a busy GitLab journal, every pull re-scans the same head window. The cost is unmeasured.
- If the key-to-agent binding stays name-based (agent-dispatcher.ts:2935), renaming an agent or a key silently breaks dispatch or pairing. Adding a real FK changes behaviour for existing name-matched keys unless it is backfilled with care.
- Scope creep: putting delivery modes, typed actions, a2a, Brain injection and pairing UX into one change removes clean rollback points. Each slice needs its own default-off flag.
- Delivered payloads carry untrusted inbound text. I found no shared fencing utility on the consumer pull/SSE path (grep hits were only in the dispatcher and connectors). If fencing is left to each harness, at least one of 40 harnesses will skip it.
Required conditions:
- Slice 1, ownership. Add a nullable agent_id (or treat owner_key_id as the identity) on durable_consumers. Pull, ack, delete and stream are allowed only for keys bound to that agent. Rows with a NULL instanceId (custom.*, connector.event) are filtered by the agent's declared types and payload conditions, not dropped by the instance IN clause. Ship it as an additive, idempotent, default-off migration on the 0082 template. Cover it in event-consumers-scoped.test.ts and event-consumers-postgres.test.ts, including a test that a custom.gitlab.* row with a NULL instance is delivered to its owning agent and refused to any other key.
- Slice 2, credential binding. Add a nullable api_keys.agent_id (FK to agents.id) and mint a durable child key per agent through POST /keys/children (0088 lineage, never wider than the parent). Backfill the existing name-matched dispatcher keys before any code depends on the FK. Revoking the key revokes delivery.
- Slice 3, emission guard. /events/trigger and agent emissions check the bound agent's manifest publishes (absent, empty or explicit, as in agent-manifest.ts:122-136), and custom.webhook.* / custom.gitlab.* stay reserved for verified webhook sources. This must ship before any agent key gets events:write.
- Slice 4, manifest compilation. accepts entries with an explicit delivery: 'subscription' compile to an owned durable consumer through the existing reconciler. Entries without it keep compiling to call_agent exactly as today, which keeps the legacy adapter on the same declaration. Prove that recompiling an unchanged manifest stays a no-op.
- Slice 5, pairing UX. Reuse the device-code approval pattern from device-login.ts so the owner approves minting an agent key. It produces an agent principal, not an owner grant. Ship it last, because slices 1-4 can be tested with keys minted by hand.
- Fencing contract. The consumer delivery envelope marks inbound message and comment text as untrusted data, server-side and the same for every harness, so no harness has to opt in. Add a test that a delivered message.received payload carries the fence.
- Each slice has its own default-off flag and a single rollback: leave the column unset or switch the flag off. No slice changes the provider enum, routes, scopes or triggers for connectors, so the property that a connector is one boot-registered module holds.
- Evidence before rollout to the 40-agent team: run a benchmark on the postgres test harness with 40 consumers and a journal at the volume of one busy GitLab project, reporting pull latency and rows scanned per pull. Name a deferred trigger for a per-type sub-index or a shared fan-out reader if p95 exceeds an agreed bound.
Unknowns:
- Unverified: whether connector.event rows are always written with a NULL instanceId. I confirmed only that instanceId is optional on /events/trigger. I did not trace the connectors.ts emit path.
- Unverified: how a2a fits. I did not read packages/core/src/providers/a2a-provider.ts or channel-a2a, so whether an a2a agent can act as a subscription consumer or must stay a call_agent adapter is open.
- Unverified: whether actor-model.md's planned agent fields (platform_identities.agentId, senderAgentId) were ever implemented. The agents table exists (schema.ts:399-437), but I did not check those columns.
- Unverified: whether Brain's Omni lane (brain-v3 src/lib/omni/fetcher.ts) already consumes through durable event consumers or polls the chat APIs. A grep for consumer endpoints in fetcher.ts returned nothing, so the Brain-injection half of the collective-consciousness case has no proof yet.
- Unmeasured: the real cost of per-agent cursors at ~40 agents on a busy GitLab project. No benchmark or production volume figure was found.
- Unverified: retention or pruning of omni_events. payload-store.ts has per-event-type retention for payloads, but I did not establish whether journal rows behind a slow agent's cursor can be pruned before that agent acks them.
- Unverified: the profile an agent key should get. profiles.ts defines cs, personal, scout, coworker and admin with differing requiresLocks, and none is agent-specific. I did not check which one fits an agent that only subscribes and acts.

### product
Verdict: support-with-conditions
Confidence: medium
Key evidence:
- The 'declare resources' concept already exists: the agent manifest (packages/core/src/schemas/agent-manifest.ts) stores `accepts` (event type + payload filter) and `publishes` on agents.event_manifest, and `publishes` is already enforced at emission time (G4c, checkPublishAllowed). So 'agent X subscribes to Y' needs no new noun: `accepts` is that concept. The smallest extension is a per-agent delivery mode. `callback` compiles `accepts` to call_agent automations, as today (services/manifest-compiler.ts:128-144). `pull` compiles the same entries to an agent-owned durable consumer, reusing filterToConditions (manifest-compiler.ts:92).
- The async delivery primitive exists and suits harnesses with no inbound port. Durable consumers (migration 0064) keep a per-consumer journal_seq cursor and offer pull/ack plus read-only SSE. SSE streams live at most EVENT_STREAM_MAX_LIFETIME_MS (30s), then reconnect from Last-Event-ID, and the cap is EVENT_STREAM_MAX_PER_KEY (packages/api/src/services/event-consumer-stream.ts:57; OpenAPI text in schemas/openapi/event-consumers.ts:373). Pull/ack fits hook-driven sessions such as Claude Code, which can drain at SessionStart or prompt hooks. SSE fits daemons such as a Herdr bot.
- Consumers have no agent identity. durable_consumers was created as global, with no tenant_id (0064 header), and 0082 adds only scoped, instance_ids and owner_key_id. No column links a consumer to agents.id.
- The proposal fails on its headline case unless this is fixed: owned (scoped) consumers cannot receive instance-less events. streamInstanceClause (services/event-consumers.ts:188-190) returns inArray(omniEvents.instanceId, ...) for any non-null instanceIds. A row with NULL instanceId, such as custom.gitlab.* or connector.event, therefore never matches a scoped consumer.
- Ownership is enforced only for instance-restricted keys. consumerVisibleTo (services/event-consumers.ts:353-354) returns true when the consumer is unscoped OR the caller's instanceIds is null. Any instance-unrestricted key can pull, ack or delete another owner's consumer, so on a ~40-agent team one agent could advance or delete another agent's cursor.
- Device pairing already mints credentials and could pair an agent. A device-flow client that is not listed still gets one key at the full operator ceiling (packages/api/src/login/config.ts deviceKeysFor: `if (!declared) return { scopes: [...ceiling], companions: [] }`). The login route creates the key and publishes access.device_authorized with apiKeyId (routes/v2/login.ts:447-481). Nothing in that path links the minted key to an agents.id, and the client allowlist names only omni-desktop, omni-dsh, omni-cli and unfold (login/config.ts:72-77).
- Agent keys already hold events:write. The omni-dsh device client mints a companion key named 'agent' with scopes ['messages:send','events:read','events:write','instances:read'] (login/config.ts, DEVICE_CLIENT_KEYS). POST /events/trigger lives in routes/v2/webhooks.ts:201. The council brief says events:write authorizes it for any custom.* type; I did not trace the scope check myself. If that holds, an agent key can forge custom.* events that other agents consume.
- `omni connect` already means two things: with no arguments it makes a device link, and with two it wires a Genie agent over NATS (packages/cli/src/commands/connect.ts:42-63, default NATS URL localhost:4222). The Genie path is the per-framework integration the owner wants to stop adding.
- actor-model.md already defines Agent as a registered, declared principal (provider, agentType, capabilities, agentCard, ownerId, nullable instanceId, isInternal) that is parallel to Person (docs/architecture/actor-model.md:84-122). Pairing can attach a credential to this entity instead of inventing a new principal.
- a2a-implementation.md describes Omni as an A2A server that takes tasks in through message/send, message/stream (SSE) and tasks/subscribe, with pushNotifications defaulting to false (lines 22-39, 106-107). That is the inbound direction, so for the subscription model it reads as one more adapter, not a competitor.
Risks or objections:
- The headline use case fails silently. If agent consumers are built on today's `scoped` flag, GitLab, custom.* and connector events never arrive, because streamInstanceClause drops NULL-instance rows. Users would see an empty stream and no error, the same 'silently green' failure class this workspace already treats as the worst bug.
- Agents could tamper with each other's cursors: with unrestricted keys, one agent's pull/ack/delete can consume or destroy another agent's backlog (consumerVisibleTo).
- Event forgery: if a paired agent holds events:write, and /events/trigger accepts any custom.* type under that scope as the brief states (not traced here), the agent can inject events that other agents treat as authentic triggers. This is a prompt-injection amplifier inside a 40-agent collective.
- Over-broad pairing: an unlisted device client gets the whole OMNI_DEVICE_KEY_SCOPES ceiling, so reusing device pairing naively over-grants agents.
- Two delivery modes can confuse users unless the manifest makes the mode explicit and `omni agents graph` shows it. An agent could otherwise get both a call_agent dispatch and a pull delivery for the same event (double handling).
- Scope creep: the 'collective consciousness' and Brain context-injection goals could pull Brain-specific code into Omni. That contradicts the owner's own 'no direct agent integrations' direction from day one.
- Offline backlog: a Mac that sleeps for a weekend comes back to an unbounded backlog from a busy GitLab project. With no lag visibility, retention cap or skip-to-now control, a reconnecting session gets flooded with stale context.
- The per-key SSE cap (EVENT_STREAM_MAX_PER_KEY) breaks shared-key setups: if several agents reuse one key, streams start returning 429s. The model only works with one credential per agent.
- Vocabulary mismatch: manifest `accepts.filter` matches by equality only, while consumers support seven operators (eq, neq, gt, lt, contains, regex, exists). Users will either hit the weaker manifest filter or bypass the manifest and create raw consumers, which splits the single concept in two.
- Adding a third meaning to `omni connect` would make an already overloaded verb worse.
Required conditions:
- BLOCKING. Separate ownership from instance scoping. A consumer gets an owner (agent_id and/or owner_key_id) that is enforced whatever `scoped` says, and an agent-owned consumer receives NULL-instance rows (custom.*, connector.event) that match its declared types. Prove it with an end-to-end custom.gitlab.* delivery to a paired agent.
- BLOCKING. Owner checks on every key. Pull, ack, stream and delete check consumer owner == caller principal for every key, not only instance-restricted ones. Legacy unscoped consumers keep today's behaviour, so the change stays additive.
- BLOCKING. Pairing mints an agent credential bound to agents.id (one key per agent). Its scope set is narrower than the device ceiling: events:read plus ack on its own consumer, messages:send and the declared connector actions. It gets no general events:write. Any agent emission, including custom.* through /events/trigger, is gated by that agent's `publishes` manifest, reusing G4c.
- BLOCKING. Omni stops at deliver + ack, and per-agent cursor lag is visible in `omni agents graph`. Brain consumes Omni as an ordinary paired agent over the same pull/SSE surface. Omni adds no Brain-specific or harness-specific code path.
- One concept, two modes: `accepts` stays the only way to say 'agent X subscribes to Y'. A per-agent delivery field (`callback` = existing call_agent compilation, `pull` = agent-owned durable consumer) is added. call_agent and providers stay untouched as the `callback` adapter, and an event goes to exactly one mode per agent.
- Delivered payloads mark inbound message, comment and webhook text as untrusted data in a stable field (or fenced envelope) that hooks can rely on. Credentials and provider secrets never appear in delivered rows.
- Pairing gets a distinct verb, such as `omni agents pair`, reusing the device-code approval flow with a new agent client id. `omni connect` is not given a third meaning.
- Offline controls: an operator-visible lag/backlog limit per agent and a 'resume from now' control, so a reconnecting harness can skip a stale backlog deliberately rather than by accident.

### security
Verdict: support-with-conditions
Confidence: medium
Key evidence:
- Verified against omni at ee5753234 (2.261030.11). The pull/ack model already fits a Mac with no public port. Deliveries are pull/long-poll/SSE and outbound-only, with a per-consumer cursor and leases (packages/api/src/services/event-consumers.ts header and pull(), line 610). SSE lives at most EVENT_STREAM_MAX_LIFETIME_MS (default and max 30s, described as 'the revocation ceiling') and has a per-key cap (resolveStreamMaxPerKey, default 5, services/event-consumer-stream.ts:84). So a revoked agent credential stops receiving within 30s on SSE.
- DATA EXPOSURE, verified in code: an instance-restricted key with events:write can read the whole tenant's journal by pull. resolveConsumerScope returns an unscoped consumer whenever scoped is false or absent, even for a restricted caller (service test event-consumers.test.ts:435 asserts exactly this). narrowToCaller narrows only scoped consumers (event-consumers.ts:372-373). The pull path calls scanPage(consumer, limit) with no caller-instance clause (line 620). Only the SSE path adds streamInstanceClause(caller.instanceIds) (lines 744-745). So the stream is narrowed to the key's instances but pull of the same consumer is not.
- Unscoped consumers have no owner. canAccessConsumer returns true for any unscoped consumer (event-consumers.ts:353), and SCOPE_MAP maps create, pull, ack, stream and DELETE of /events/consumers to events:write (constants/scopes.ts:201-205). Any events:write key can therefore read, move the cursor of, or delete another agent's unscoped consumer.
- Scoped consumers drop rows that have no instance. instanceScopeClause uses inArray(omniEvents.instanceId, ...) (event-consumers.ts:381-383), so rows with a NULL instanceId (custom.*, connector.event) never match. The safe option today cannot subscribe to custom.gitlab.* or connector events.
- Event spoofing, verified: POST /events/trigger needs only events:write (scopes.ts:495) and accepts any custom.* eventType (CustomEventType = `custom.${string}`, core/src/events/types.ts:140). The only check is on instanceId (routes/v2/webhooks.ts:201-217). WebhookService.trigger records no producer key on the event (services/webhooks.ts:693-722). Any agent holding events:write can forge custom.gitlab.* or another agent's 'emissions', and subscribers cannot tell them from real ones.
- Connector routing is advisory for raw consumers. connectorTargetMatches returns true when targetAutomationId is missing (core/src/automations/engine.ts:46-52), and durable consumers do not apply it at all. One connector subscription mapping to one automation (D7) does not carry over to an agent subscription.
- Credentials: neither api_keys (packages/db/src/schema.ts:614+) nor durable_consumers has an agentId or any agent binding. Keys do support parentKeyId child keys, expiresAt, revocation, scopes, instanceIds, chatAllowlist and outboundRecipientAllowlist, and scope-enforcer.ts enforces those locks deny-by-default. These are the right building blocks to bound what an agent can do (say/send).
- Device pairing already exists and is human-approved. It is the Better Auth device flow, approved by the owner's own fresh text in their WhatsApp self chat or by `omni approve` (plugins/device-login.ts header). Device keys are capped by OMNI_DEVICE_KEY_SCOPES, may never carry *, keys, settings, auth, trust, audit or platform scopes, and have an optional TTL (login/config.ts:159-198). But DEVICE_CLIENTS is a closed list (omni-desktop, omni-dsh, omni-cli, unfold; config.ts:72-77), so pairing a new agent harness would need a code change.
- Precedent and warning: the Unfold 'agent' companion key already carries messages:send, events:read and events:write (login/config.ts:98-99). Every gap above (pulling the whole journal, taking over unscoped consumers, forging custom.* events) is already reachable by a key meant for an agent.
- Untrusted text: no general fence exists on the delivery path. The only 'untrusted' handling in core/api is C0-control stripping in providers/openclaw/provider.ts:21. Consumer pull returns the journal row as stored, so message and comment text reaches agents unfenced.
- actor-model.md is marked 'status: wish ... aspirational, not yet implemented' (docs/architecture/actor-model.md:1-12). There is no implemented agent principal to reuse. identity-graph.md has no agent or principal concept (grep found none).
Risks or objections:
- Cross-instance data exposure, already live. Pairing ~40 agents on instance-restricted events:write keys would give each one read access to every instance's messages in the tenant, through an unscoped consumer plus pull. This is the most serious issue, and it exists before any new feature is built.
- Consumer takeover between agents. Any agent's key can ack past (silently dropping) or delete another agent's unscoped consumer. With Brain injecting deliveries as context, an attacker can starve an agent of events or skip it past them.
- Forged events become injected context. A compromised or prompt-injected agent with events:write can publish custom.gitlab.* or fake 'agent emission' events. Brain would then inject them as trusted context into ~40 sessions. Because there is no producer attribution, the forgery cannot be traced.
- Prompt injection spreading across the collective. Inbound WhatsApp, Slack or GitLab comment text is unfenced. Through Brain context injection, one hostile message can reach many agents at once, and each holds an outbound say/send verb. That is a wormable path: an injected agent emits an event that injects the next one.
- Subscription filters treated as authorization. Type globs and payload conditions are filters, not access control. If 'declared resources' only become consumer filters, an agent can re-declare its way to more data. The declaration must be enforced by the server against what the credential is allowed.
- Fail-closed rows push operators toward unscoped consumers. Because scoped consumers cannot see custom.* or connector.event rows, operators will create unscoped ones for GitLab and connector feeds, which re-opens the exposure above.
- Credential sprawl. Without an agentId binding, a 'paired agent' is just another api key. Revocation, audit and `omni agents graph` cannot tell which harness acted, and child keys cascade only from their parent.
- Pairing approval spoofing or fatigue. 40 agents pairing through owner self-chat codes invites approvals given without looking. Herdr bots with permanent identities need TTL and rotation, not the default null TTL (deviceKeyTtlDays nullable).
- The legacy call_agent adapter's credentials. If the adapter runs on the new subscription model, provider credentials (agno and webhook secrets, NATS) must stay server-side in the adapter and never appear in delivered rows.
Required conditions:
- Fix before pairing any agent. Either apply the caller's instance clause on pull exactly as the stream does, or force instance-restricted keys to create scoped consumers. Add a regression test showing a restricted key cannot pull another instance's rows.
- Give every consumer an owner. An agent consumer stores ownerKeyId and agentId, and only that owner (or an admin or owner-tier key) can pull, ack, stream, inspect or delete it. Unscoped and unowned consumers stay as they are for legacy keys only, and agent credentials cannot create them.
- Bind the agent principal to its credential. Add agentId on the paired key, or have the consumer reference agents.id, so every delivery, ack, say/send and trigger is attributed to one agent and can be revoked per agent. Agent keys get a mandatory expiresAt and rotation, and never carry keys, settings, auth, trust, audit or platform scopes, matching the device-key ceiling.
- Treat declarations as authorization, checked by the server. The resource set an agent declares (event types, instances, webhook sources, connector keys, other agents' emissions) is approved by the owner at pairing. The server then intersects it with every consumer filter, so the agent cannot widen it with globs.
- Fix provenance before letting agents consume custom.* or emissions. Either restrict POST /events/trigger for agent keys to their own namespace (e.g. custom.agent.<agentId>.*), or add a separate scope such as events:trigger. Stamp the producing key and agentId on every event, so subscribers and Brain can tell webhook-sourced custom.gitlab.* from forged events.
- Give scoped consumers a non-instance scope dimension (webhook source id, connector key, producing agent). Agents can then subscribe to custom.* and connector.event without falling back to unscoped consumers.
- Fence delivered content. Every inbound message, comment or webhook text field in an agent delivery is marked as untrusted data (envelope field plus a framing contract), and Brain keeps that fence when it injects context. Agents' outbound verbs stay bounded by chatAllowlist and outboundRecipientAllowlist on the agent key.
- Make pairing reuse the device flow. Owner approval follows the self-chat or `omni approve` path, and the approval screen shows the declared resources and verbs. Generalise DEVICE_CLIENTS to a registered agent client class, so a new harness needs no per-framework code.
- Keep the legacy provider/call_agent path as a server-side adapter that consumes the same subscription model. Provider credentials stay in the adapter and never appear in rows delivered to agents.
- Name the deferred triggers: a shared consumer group per agent (when one agent runs many sessions); quotas per agent for streams and cursors (when the agent count goes past the per-key SSE cap of 5 per key); a hash-chained audit of agent actions (when an agent can act without a human in the loop).
Unknowns:
- Unverified: whether a2a (scopes.ts:45-46, a2a-provider.ts) can be expressed as an async subscription plus a typed action, or needs its own synchronous adapter.
- Unverified: whether the tenant RLS boundary (runTenantWorkDb or scopedHandle) fully holds for pull under the default deployment. The pull exposure is assessed as within one tenant only.
- Unverified: whether connector.event or webhook-sourced journal rows can carry secrets or raw provider headers in their payload, which would reach any agent that pulls them.
- Unverified: the cost of ~40 per-agent cursors against a busy GitLab project's event volume. scanPage is an indexed scan by journal_seq per consumer, but I measured no load.
- Unverified: whether the nats-genie provider's NATS connection has auth or TLS outside localhost. Only test scripts show the nats://localhost:4222 default.
- Unverified: whether Brain's context injection already fences Omni-sourced text as untrusted on its own side.
- Unverified: whether the Better Auth device flow allows adding a client_id at runtime, or whether DEVICE_CLIENTS can only change through a code change (it appears to be a const).

### dissent
Verdict: oppose
Confidence: medium
Key evidence:

It also re-homes call_agent as an adapter on the new model, and adds a 40-agent Brain injection loop. The path it would re-home is packages/api/src/plugins/agent-dispatcher.ts, 6,801 lines. Rebasing that path onto the journal is a re-platform, not an extension.

The smallest single-concept change is to let `accepts` compile into a durable consumer bound to the agent instead of call_agent. Building a parallel pairing and declaration model is not that change.

An agent that declares several resources (chat messages, custom.gitlab.*, connector events, another agent's emissions) needs N consumers with N cursors and no single ordered stream. That breaks the 'agent X subscribes to Y is one concept' goal on today's substrate.

The user's global CLAUDE.md, finding 1, records 1,006 polling-only API responses and about 250M context tokens wasted in this host's Claude Code sessions. A Claude Code session cannot be pushed to between turns, so 'this specific Claude Code as a subscriber' depends on in-session waiting or a supervisor daemon. Risks or objections:

The turn context bound to api_keys is the most likely place to break: omni say/done, debounce, sessions and reply-to-chat.

## Synthesis
Decision: proceed-with-conditions
Consensus: All five lenses agree on the direction: an agent should hold a credential, declare what it consumes, and receive deliveries asynchronously and outbound-only. Four lenses support it with conditions (architecture with high confidence; delivery, product and security with medium). Dissent opposes the proposal as framed but agrees with the same direction once it is made smaller. The lenses also agree that most of the machinery already exists in Omni 2.261030.x:
- durable consumers with a journal_seq cursor, pull/ack, long-poll and SSE, delivered at-least-once with leases;
- the agent manifest's accepts/publishes, compiled by a reconciler that only touches the rows it manages;
- api_keys parentKeyId child keys plus their locks (chatAllowlist, outboundRecipientAllowlist);
- device-code owner approval.
So the work is to extend these, and no new subscription table or principal type is needed.

Every lens found the same blocking gaps in today's code:
1. Durable consumers have no agent identity, and api_keys has no agentId.
2. Unscoped consumers have no owner. canAccessConsumer returns true, so any events:write key can pull, ack or delete another consumer (event-consumers.ts:353).
3. Scoped consumers silently drop rows with a NULL instance_id (instanceScopeClause, event-consumers.ts:381-383). That makes custom.gitlab.* and connector.event, the headline use case, unreachable without any error.
4. POST /events/trigger accepts any custom.* type under events:write, does not check publishes, and does not record which key or agent produced the event. A paired agent could therefore forge events that other agents trust.
5. Delivered rawPayload text has no fence marking it as untrusted, so it reaches Brain's context injection unmarked.
6. The existing 'agent' companion key (DEVICE_CLIENT_KEYS.unfold) already holds events:write, so every one of these gaps can already be reached today.

All lenses also agree that the legacy providers and call_agent stay unchanged in behaviour. No provider enum value or dispatcher case is removed, and the new path adds none.
Dissent:
